# Стресс-тест сервера

`solbreaker benchmark` запускает карты и физику из совместимой сборки Blitz, готовит
временные данные сервера и по умолчанию использует профиль лаунчера
с отдельным процессом на каждую арену и физикой Bullet. Для контрольного прогона
с общей петлёй сервера укажи `--engine in-process`. Игровой клиент
запускать для теста не требуется.

## Быстрая проверка

Windows, из распакованной папки Solbreaker в PowerShell

```powershell
.\runtime\python\python.exe -m solbreaker benchmark --game "D:\Games\Blitz" --output benchmark.json
```

Linux, из папки подготовленной установки

```bash
.venv/bin/python -m solbreaker benchmark --game "/path/to/Blitz" --output benchmark.json
```

В `--game` укажи папку с `wotblitz.exe` и `Data`. По умолчанию тест использует
Рудники и сценарии `solo,bots`. После восьми секунд прогрева он измеряет нагрузку
30 секунд. Рабочие аккаунты, настройки и файлы игры остаются в своих папках. Тест открывает UDP
только на loopback и пишет временные данные в системную папку. Для диска
с большим запасом места укажи существующую папку через `--work-dir`.

Рядом с `benchmark.json` появится автономный `benchmark.html`. После прогона
из лаунчера отчёт откроется в браузере по умолчанию. Для повторного просмотра
в журнале есть кнопка **Открыть отчёт бенчмарка**. HTML работает
офлайн и показывает итоги отдельных прогонов, статистику арен и сетевые
счётчики. Для графиков CPU, RAM, частоты и задержек новые прогоны сохраняют
секундные замеры в поле `timeline`. Замеры дочерних процессов видны там,
где их счётчики доступны.

Во время прогона в журнале видны примерное время до конца всей матрицы,
ОЗУ и загрузка ЦП процессов бенчмарка. 100% ЦП соответствует одному
логическому ядру. Кнопка **Остановить** завершает работу на ближайшем
безопасном этапе и сохраняет завершённые прогоны. Неполный HTML можно
открыть из журнала.

Уже сохранённый JSON можно открыть как HTML без нового прогона

```bash
python -m solbreaker benchmark-report benchmark.json
```

В старых JSON графики используют доступные десятисекундные окна.

## Матрица нагрузки

Флаги ниже можно добавить к команде для своей ОС. Для каждой комбинации карта,
сценарий, число арен выполняются заново. Повтор использует следующий seed.

```text
--maps rudniki,himmelsdorf --scenarios solo,bots,players --arenas 1,2,4 --seconds 60 --warmup 10 --repeat 3
```

- `solo` — один танк под управлением сценария и неподвижная мишень.
- `bots` — один танк под управлением сценария и до 13 ботов Classic AI.
- `players` — до 14 тестовых сессий с движением, прицеливанием и выстрелами.
  Тестовые сессии обмениваются штатными зашифрованными UDP-пакетами с сервером.
  Число танков зависит от лимита карты.
- `--input-pattern burst` отправляет управление от всех сессий одновременно
  в каждом слоте 30 Гц. `--input-pattern spread` разносит отправки внутри слота
  и чередует арены. Сравнивай также фактическое число принятых команд.
- `--tanks 2,8,14` сравнивает плотность боя. Применяется к `bots` и `players`,
  учитывает вместимость карты и сохраняет равные команды. В `solo` всегда
  два танка. Стенд принимает до 16 арен для замеров предела. Пиковый расход памяти зависит от карты и числа процессов.
  Штатный лаунчер по умолчанию разрешает одну активную арену.
- `--cold` запускает фоновый разбор каталога карт, как при старте лаунчера.
  Обычный прогон измеряет бой с уже подготовленными метаданными выбранной карты.
- `--diagnostic-dir ПАПКА` записывает фазовые трассы сервера и процессов арен
  в новую папку. Запускай такой профиль отдельно от замеров производительности,
  поскольку подробная трассировка добавляет нагрузку.
- Для продолжительного прогона выбери один сценарий и задай `--seconds 900` или
  больше. Сравни одинаковые параметры на разных ПК. При запуске игры на том же ПК
  прогони отдельно с игрой и без неё, чтобы увидеть эффект общей нагрузки.

## Как читать результат

- `steps_per_second` и `dropped_seconds` относятся к каждой арене отдельно.
  Ожидаемый темп — 60 физических шагов в секунду. Потерянное время означает,
  что движок отбросил часть накопившейся работы.
- `tick_work` — длительность работы серверного callback. `loop_delay` —
  опоздание планового задания с вводом. `input_queue` — от постановки команды
  в очередь до обработки её пачки, а в режиме owner до подтверждения
  обработки команды процессом арены. `motion_gap` — паузы между отправленными
  обновлениями движения. Время в этих полях указано в миллисекундах.
- `server_rtt_at_end` показывает сглаженный RTT тестовых сессий в конце прогона.
  На Linux поля `server_udp_receive_drops` и `peer_udp_receive_drops` содержат
  потери в буферах UDP-сокетов сервера и тестовых клиентов соответственно.
- `owner_step_roundtrip` показывает p50, p95 и p99 пути шага от постановки
  в очередь до доставки результата. Это суммарное время очереди, IPC,
  расчёта и доставки. Фазовую стоимость даёт трасса.
- `windows` показывает темп каждой арены, число сессий и накопленное
  сброшенное время по окнам в 10 секунд.
- `build_seconds` и `shutdown_seconds` показывают запуск и остановку
  конкретной арены. На уровне прогона `shutdown_seconds` включает закрытие
  транспорта, процессов и временного хранилища сервера. Кэш карт
  используется повторно внутри одного запуска. Первый проход может быть холодным.
- `cpu_cores_avg` — средняя загрузка именно процесса, где 1.0 соответствует
  одному полностью занятому ядру. Процесс включает сервер и тестовые сессии.
  RSS относится к этому же процессу. В режиме owner он измеряется отдельно
  от дочерних процессов арен. На Linux отчёт отдельно включает суммарные
  `arena_worker_cpu_cores_avg` и `arena_worker_rss_bytes_sum`. Сумма RSS может
  учитывать общие страницы несколько раз. Пик RSS родительского процесса
  считается с запуска программы, включая предыдущие сценарии.
- `max_below_heightmap_m` и `max_below_heightmap_seconds` отмечают,
  насколько глубоко и как долго наблюдаемая позиция корпуса находилась больше
  чем на метр ниже высотной карты. Сигнал стоит сверять с рельефом и
  коллизиями объектов.
- `overloaded` означает потерю темпа, отброшенное время или переполнение очереди.
  Значительная потеря команд между отправителем и очередью также даёт `overloaded`.
  `stalls` означает длинные паузы при обработке ввода или публикации движения.
  `fault` означает ошибки сервера, потерю тестовых сессий или некорректную
  позицию. Пороги — ориентир для сравнения двух прогонов.

JSON сохраняется после каждого сценария. Поле `complete` становится `true` по завершении всей матрицы.
В отчёте указаны параметры нагрузки, модель процессора, ОС, версии и измерения.
Пути установки и данные аккаунтов в него не попадают. Отчёт можно приложить к
issue. Если именно игровой клиент всё ещё дёргается при хорошем результате
теста, для диагностики нужен отдельный прогон реального боя и журнал сервера.
Сессии создаются стендом. После этого команды, обновления и подтверждения
идут через localhost UDP. Внешняя сеть, вход в аккаунт, создание игровых
сущностей у клиента и отрисовка лежат за пределами этого измерения.

Сокетный IPC процессов арен по умолчанию группирует команды ввода. Параметр
`SOLBREAKER_OWNER_INPUT_BATCH=0` возвращает передачу по одной команде для
контрольного замера. Сценарии сравнивай на одинаковых карте, seed и
длительности. Пакет включает до 16 уже принятых команд управления,
наведения и стрельбы. Шаги и операции жизненного цикла сохраняют свои места
в очереди. Авторизация всех команд проверяется перед передачей пакета,
а при публикации сверяется текущая сессия получателя.
